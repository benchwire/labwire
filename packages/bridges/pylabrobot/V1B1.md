# PyLabRobot v1b1: compatibility assessment

**Status: EXPERIMENTAL, branch `plr-v1` only. Nothing here is published
to PyPI.** PyLabRobot is being redesigned on its `v1b1` branch, which
the maintainer force-pushes while it is in flight. Released
`labwire-pylabrobot` pins `pylabrobot>=0.2,<0.3` and targets the
LiquidHandler API; released users are unaffected by anything in this
document. The `plr-canary` workflow on `main` re-measures the facts
below daily.

Pinned upstream states this assessment was written against, refreshed
deliberately, never automatically:

- `PyLabRobot/pylabrobot` branch `v1b1` at commit `1ae9dc6aec09`
  (2026-08-01). TODO-VERIFY on every refresh: the branch moves and is
  force-pushed; whatever it says today wins over this document.
- PR [#1184](https://github.com/PyLabRobot/pylabrobot/pull/1184)
  (vcjdeboer's Opentrons Flex plain-class driver) at head commit
  `6ee378e5af67`. The PR base is an older v1b1: the maintainer
  force-pushed the base twice on 2026-08-01, and the PR is currently
  not mergeable until rebased. The Flex driver exists only in this PR,
  not on `v1b1` itself.

## The redesign, as it stands at the pinned commit

A device driver becomes one plain Python class per device: no base
class, no registry, no capability descriptors, no serialize, no async
context manager. The contract is convention: `async setup()` /
`async stop()`, a `self.io` transport from `pylabrobot.io`, and public
async operation methods. The `capabilities/` package that briefly
existed on this branch was deleted on 2026-07-31; anyone who coded
against it in July has had the floor removed, which is what tracking a
force-pushed branch means.

The LiquidHandler world is moved, not deleted: `LiquidHandler`, its
backends, and the chatterbox simulator live intact under
`pylabrobot.legacy.liquid_handling`, and the old import paths still
work through shim modules that raise `DeprecationWarning`. No
plain-class successor for a Hamilton-style liquid handler exists at the
pinned commit; the Flex PR is the first plain-class liquid handler.

## What the shipped bridge assumes, versus what survives

Measured, not guessed: the shipped bridge test suite runs against v1b1
at the pinned commit with **110 of 113 tests passing** through the
legacy shims (see the canary report for the live number).

| Shipped-bridge assumption | v1b1 reality at `1ae9dc6` |
|---|---|
| `LiquidHandler` frontend with the 0.2 method surface | Intact under `pylabrobot.legacy`; old paths shimmed with `DeprecationWarning`. One shim is missing: `pylabrobot.liquid_handling.errors` has no shim, so the `ChannelizedError` import path is gone (1 test failure). |
| Frontend/backend split (`lh.backend`, `num_channels`) | Legacy only. New-style drivers have no backend object; the split is explicitly deprecated by the device-driver guide. |
| Deck read by attribute traversal (`get_all_children`, `category`, `model`, `get_absolute_location`, `get_size_*`, `num_items_*`); the bridge never calls `serialize()` | Survives. `pylabrobot/resources` was not moved to legacy; `Resource`, `Deck`, traversal, and serialization all present and runtime-verified round trip. Decision to traverse attributes rather than consume `serialize()` output turns out to be the durable choice. |
| Labware `model` strings stable enough to key annotations | Not stable: factory renames change the model string (`Cor_96_wellplate_360ul_Fb` now yields `cor_96_wellplate_360uL_Fb`; 76 "will be removed in v1b1" markers; the classic Hamilton tip-rack short names now hard-raise). The rename accounts for 2 test failures, and one of them is the sharp one: a model-keyed `locked` annotation **silently stops matching**, because an annotation keyed on an upstream string has no integrity check. |
| Tip and volume trackers readable for deck state | Survive unchanged in `pylabrobot/resources`, readable with no LiquidHandler at all (runtime-verified). Module-level `set_tip_tracking` / `set_volume_tracking` toggles unchanged. |
| One PLR import in bridge source (`set_tip_tracking`, `set_volume_tracking`) | Still valid. The bridge source imports cleanly against v1b1 today. |

## The brief's three questions, answered

**Does the resource tree / Deck model survive well enough for the deck
projection and typed references to port?** Yes, verified twice over:
the shipped projection runs against v1b1 through the shims, and the
experimental bridge (below) reuses the same `introspect`, `deck`, and
`addressing` modules against a `FlexDeck` with no changes to any of
them. `FlexDeck` is a `Deck` subclass whose slots are ordinary child
resources, so typed well references validate against it exactly as
they do against a STARlet deck.

**What replaces the LiquidHandler as the natural one-instrument
unit?** The device class instance itself, with one wrinkle: the device
instance alone is not enough. The resource machinery needs a deck root
and a channel-state reader, and the plain-class model standardizes
neither. `OpentronsFlex` happens to hold `self.deck`; nothing says the
next device will, and no protocol adapter can rely on it. The
experimental bridge therefore binds `(device, deck)` explicitly.

**Where do trackers live and can telemetry read them?** Tip and volume
trackers still hang off `TipSpot` and `Container` in the resource
tree, and the deck projection reads them exactly as before. What moved
is channel state: `LiquidHandler.head` is legacy, and the Flex driver
keeps channel-to-tip assignment in a private `_channel_tips` list.
There is no public reader for "what does channel 3 hold" in the
plain-class model; the experimental bridge reads the private attribute
and says so out loud.

## What the plain-class model takes away from an adapter

The new model is deliberately uninstrospectable: there is no base
class, descriptor, or registry to reflect over, only the class's own
methods and type hints. The shipped bridge already treated
LiquidHandler's surface as "one fixed class, nothing to discover"
(`command_surface()` is a hand-written table), so for us this is a
confirmation, not a loss: **in the plain-class world, every device
bridge is a curated command table**. The typing, units, safety
classes, and cancel semantics all come from the Labwire side, which is
exactly the division of labor this protocol was built around.

Identity is thinner: a plain device has no `name`, serial, or model
attributes by convention. The Flex driver exposes `robot_model` and
`api_version` only after `setup()` has talked to the robot.

## The experimental plain-class bridge: what building it proved

`plainclass.py` in this package (branch `plr-v1` only) maps vcjdeboer's
`OpentronsFlex` to a Labwire instrument and passes an 11-test suite run
entirely against a simulation of the Opentrons robot-server command
layer (`tests_flex/opentrons_sim.py` fakes the exact HTTP endpoints the
driver uses, so the tests assert on the precise command stream a robot
would have received). That mirrors how the PR itself was validated; no
hardware behavior is claimed by either side.

What held:

- **The deck machinery ported with zero changes.** `introspect`,
  `deck`, and `addressing` from the shipped bridge run unchanged over a
  `FlexDeck` through a 60-line view (`DeckBoundDevice`) that binds the
  device to its deck. Typed well references validate against the Flex
  deck exactly as against a STARlet; a bad reference is refused before
  any HTTP command is issued.
- **The command discipline transferred whole.** Same UCUM unit tables,
  same safety classes, and the same cancellation truth: every atomic
  Flex call is one HTTP command that is committed once posted, so all
  of them declare `cancel_semantics: "none"`, and the two
  bridge-sequenced commands (`transfer`, `discard_tips`) declare
  `between_steps` and prove it: a cancel during a held aspirate
  settles `halted_at_boundary` with the boundary named, the next step
  never issued, and the source well's deficit visible in the deck
  resource. The F10 field report was from a Flex owner; the Flex
  bridge honoring it is the loop closing.
- **The annotation format needed no changes.** Same YAML, same checks.

What strained, recorded plainly:

1. **Channel state has no public reader.** Which channel holds a tip
   lives in the driver's private `_channel_tips`; the bridge reads it
   and says so. `LiquidHandler.head` was public; the plain-class world
   has no equivalent convention yet. The list is also a fixed 8 slots
   whatever pipette is mounted, so the bridge clamps its channel
   projection to the discovered pipette's channel count.
2. **The device instance alone is not an instrument.** The resource
   machinery needs a deck root; `DeckBoundDevice` exists because
   nothing in the plain-class model carries one by contract.
3. **The PR head cannot import its own legacy tree.** At the pinned
   commit, `import pylabrobot.liquid_handling` fails from an installed
   copy (`pylabrobot.molecular_devices.imageXpress` is missing from
   the package), which is why the experimental tests live in their own
   directory, out of reach of the shipped tests' conftest (it imports
   LiquidHandler at module scope). The Flex driver itself is
   unaffected. TODO-VERIFY after the author rebases onto current v1b1.
4. **Multi-element calls would be recorded but not executed.** At the
   pinned commit the driver builds each robot command from element [0]
   of its list parameters while committing tracker state for every
   zipped element, so a multi-well aspirate would record liquid the
   robot never moved. The bridge refuses any multi-element call
   (`DeckBoundDevice._single`) until the driver executes batches; a
   test proves the refusal reaches the agent before any HTTP command
   is issued. The driver's own PR describes itself as
   single-channel-first; the silent tracker commit is the sharp edge.
5. **Command surface is curation, not discovery, permanently.** The
   experimental bridge's `flex_command_surface()` is a hand-written
   table, like the shipped bridge's, and in the plain-class world that
   is now the only possible design. Labwire supplies the typing; the
   driver supplies the physics. No protocol change needed; the
   division of labor just became explicit.

## What must happen upstream before this exits experimental

1. The `v1b1` branch stops being force-pushed, or grows release tags
   that can be pinned honestly.
2. PR #1184 (or an equivalent plain-class liquid handler) is merged,
   so the target device exists on the branch rather than in an
   unmergeable PR.
3. A public convention exists for channel state (today it is a private
   attribute) or the bridge accepts telemetry loss there.
4. A PLR release carrying the redesign appears on PyPI, so the shipped
   extra can express a real version bound instead of a git pin.
